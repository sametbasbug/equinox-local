# `eqlocal` — local agent CLI

`eqlocal` is a JSON-first command-line client for the **existing running** Equinox Local runtime. On macOS Factory/source checkouts, startup installs `~/.local/bin/eqlocal` as a user-owned launcher bound to the running source checkout and the running Node executable; no signed managed-release layout or ambient PATH Node is required. You can also invoke `node scripts/eqlocal.mjs` from the checkout. It does not launch a second agent or provide a new ChatGPT API. Managed signed releases use their own pinned Node and managed launchers. This CLI shares the existing local authenticated bridge; it is not a second server or independent agent.

## Contract

- Success: exactly one `{ "ok": true, "result": ... }` JSON object on stdout. Errors: exactly one `{ "ok": false, "error": { "code": ..., "message": ... } }` on stderr and nonzero exit status. `--json` is an explicit supported no-op, because JSON is already the default. `--help` prints usage.
- No interactive prompts, ANSI UI, progress spam, implicit selection of a browser tab, or automatic retry of browser mutations. Supply `--request-id` if a caller needs deterministic retry protection across process crashes.
- It talks to a same-user, token-authenticated local IPC bridge. The descriptor is stored in Equinox Local's **existing private application state**, not in the repository. macOS uses an owner-only Unix socket; Windows uses a randomized named pipe. The running runtime must be available and the ChatGPT browser context must be connected for chat commands.
- Commands are usable by any local process with access to that signed-in user's private EL runtime. Existing EL Agent Access/Emergency Stop/operation guards apply. `--agent NAME` adds an informational ChatGPT message prefix; it is not a separate permission system.

## Tools

```console
$ eqlocal status
$ eqlocal tools list
$ eqlocal tools list runtime
$ eqlocal tools list desktop
$ eqlocal tools describe runtime.terminal_exec
$ eqlocal call runtime.system_doctor
$ eqlocal call runtime.terminal_exec --args '{"project":"home","command":"pwd","shell":"zsh","cwd":".","wait_ms":10000,"max_output_chars":4000}'
$ eqlocal call runtime.task_list --args-file -
```

On Windows, **PowerShell callers use `eqlocal.ps1`**. The launcher always preserves the argument array, even when the caller passes zero or a single argument (`--help`). The launcher accounts for Windows PowerShell 5.1 legacy native-argument quoting and PowerShell 7+ so quoted JSON passed to `--args` survives; CMD callers use `eqlocal.cmd` and should prefer `--args-file -` for JSON. The PowerShell script is locally generated by the signed installer, not downloaded separately. If a shell inherits an old user PATH, open a new session or use the absolute product-bin path until the Windows environment refreshes.

`tools list` also discovers the `desktop` domain when available. `tools list <domain>` and `tools describe domain.operation` use the **live** capability catalog, including input JSON Schemas. The generic `call` command delegates to the same tool handler as ChatGPT; operation errors retain their existing boundaries. For cross-platform commands, use the `shell` and argument schema returned by the connected host rather than assuming POSIX syntax on Windows.

## Tasks & Chat

```console
$ eqlocal tasks create --title "Review" --objective "Review the architecture"
$ eqlocal tasks list --status active
$ eqlocal tasks read task-...
$ eqlocal chat start --task task-... --wait
$ eqlocal chat start --task task-... --run-task
$ eqlocal chat send --task task-... --agent Nyx --message "Selene, feedback?" --wait
$ eqlocal chat send --task task-... --message-file - --request-id 0123456789abcdef
$ eqlocal chat wait --task task-... --receipt '{"userEpoch":"...","previousAssistantTurnKey":"..."}' --timeout 120
$ eqlocal tasks finish task-...
$ eqlocal tasks delete task-...
```

`tasks delete` accepts only completed/cancelled Task Capsules; active tasks must be finished or cancelled first. This is the same store invariant as Control Center, not a separate deletion mechanism.

New tasks are created first, then explicitly opened with `chat start`; existing bound tasks can be addressed through `chat send`. By default, `chat start` sends a short, tool-free ready handshake rather than immediately executing the Task Capsule objective, avoiding recursive agent starts. Use `--run-task` to intentionally start executing the objective in the new chat (same existing behavior as Telegram task chat). `chat start` reuses the Telegram Task Chat Browser primitives but does **not** send a Telegram message. Both use exact task/chat bindings.

`chat send` yields a receipt containing `userEpoch` and `previousAssistantTurnKey` upon confirmed delivery. `--wait` polls for the completed assistant response for up to 120 seconds by default (maximum 600). If no answer is ready, it returns a waiting status **with the original receipt**, which the caller can supply to `chat wait` to resume reading. Do not re-send a message simply because reading timed out. On an uncertain send failure, inspect the ChatGPT task conversation before repeating, using the same `--request-id` if an explicit retry is truly warranted; the extension suppresses duplicate delivery IDs.

**Browser extension compatibility:** The installed Chat Bridge v9 has an exact-composer comparison issue with multiline messages: ChatGPT renders separate `<p>` paragraphs and `textContent` concatenates them. A source fix is included in the browser extension and must reach users through the normal Chrome Web Store update path before multiline CLI sends are reliable; use a single-line message until that update is published. CLI agent attribution stays on the first line for compatibility with the currently installed extension. Ambiguous delivery means **do not automatically retry**: inspect the exact task chat before sending again.

The Browser response reader currently returns at most 12,000 characters of the latest completed assistant turn; `truncated` signals when the browser output exceeded that limit. This is not a transcript export API.

## Implementation and verification notes

- Completed in source: signed Main install writes `eqlocal` shims that invoke **the product-owned pinned Node**, not global Node/npm; uninstall removes the exact owned shims. macOS installs `~/.local/bin/eqlocal` and a marked PATH line in `~/.zprofile`; Windows installs `<LOCALAPPDATA>\Equinox Local\bin\eqlocal.cmd` and adds that directory to current-user PATH. Newly opened terminals pick up the PATH update.
- Verified in development: an unsigned darwin-arm64 native release archive was built by the product packager from `7658433`, validated with all 150 source files, and its temporary artifacts removed. This is not equivalent to a signed native install or Windows acceptance.
- Verified live: neutral `chat start --wait` returned exact `EQL_CLI_READY` without creating another Task. The temporary Task and tab were removed.
- Verified isolated macOS native package lifecycle: bundled pinned Node v26.12.1, CLI launch, reinstall and PATH/uninstall cleanup. Candidate is unsigned, not a production install.
- All four native candidate builds passed on [CI run #40891590509](https://github.com/sametbasbug/equinox-local/actions/runs/40891590509); production publication was skipped.
- Signed Main installed runtimes automatically reconcile the owned `eqlocal` launcher to the **currently authenticated native release** shortly after startup, after the A/B owner marker is released. The same reconciliation applies after a successful update or an authenticated A rollback; Factory/source runtimes reconcile their own `~/.local/bin/eqlocal` on macOS startup to the exact running source CLI and Node, using the same ownership checks and marked profile block; they do not impersonate a signed managed release. Launcher refresh failures are optional and never roll back a healthy Equinox Local runtime. This startup path still requires signed update/rollback device acceptance before production.
- Verified on the actual Windows machine with the product-owned Node v26.12.1 copied into an isolated release layout: the source installer generated PowerShell/CMD launchers; zero/one/multiple args, JSON and Unicode passed in PowerShell 5.1 and 7, and reinstall/uninstall cleaned both launchers and the temporary user PATH entry. The installed public product was unchanged.
- Installed public Windows and macOS environments have been exercised separately. Public macOS VM installation and the independent native-SHA admission fix were confirmed after signed Main publication; actual device diagnostics and settings preservation should still be checked when investigating a new install failure. CLI and Browser chat operations are guarded by the same underlying runtime rather than a new agent process.
- Check the independent browser extension's current Chat Bridge version; do not modify CWS packaging without a separate browser release.
- Later: MCP transport for agent callers may delegate to this same local dispatcher without duplicating feature implementations.

## Factory/source-checkout macOS launcher

Source-checkout startup now reconciles the same user-owned `~/.local/bin/eqlocal` symlink and marked `~/.zprofile` PATH entry as the managed macOS install. The product-owned launcher under `~/Library/Application Support/Equinox Local/bin/` executes the **actual running source checkout** `scripts/eqlocal.mjs` using the **actual running Node binary** resolved by `realpath`, never a global PATH lookup or a fictitious signed release. Preexisting foreign commands or unsafe files are not overwritten; launcher setup errors remain optional and do not disable the runtime. The private IPC descriptor and token remain under application state, not in the launcher. This was checked against the Mac mini Factory runtime: `eqlocal status` returned connected/protocol 1 with all six capability domains, and a fresh zsh login shell resolved the command. No runtime restart was needed to provision the missing command immediately; future source startups perform the same reconciliation automatically.
