# Equinox Local Chat: native conversation workspace

Status: **design corrected 2026-11-21; not implemented or released.** User reference: [Chat On Steroids](https://github.com/totec448-spec/chat-on-steroids). This page supersedes the earlier embedded-ChatGPT-web proposal.

## What the user means

Build an **Equinox-designed, Codex-like chat interface** in the existing Electron Control Center: independent thread list and chat composer, message stream, intermediate progress and native tool/action cards, conversation selection, task association, and clear paused/running/completed states. This is **not** `chatgpt.com` rendered in `WebContentsView`, nor an iframe, nor a link to a browser window. The visual companion selector remains independent from the choice of underlying conversation/agent.

Keep the product's existing authenticated current-user IPC, `equinox://control/` bundled UI, one runtime owner, Browser extension bridge, security policy, Main signing/update gates and source Factory identity. Do not create another localhost web server, extra anonymous agent service, test suites or storage of passwords/session cookies.

## Reference project: what it actually does

As documented by Chat On Steroids, its own Electron UI controls and records ChatGPT conversations through **a browser extension that observes and automates the ChatGPT page**. Its local MCP tools run in the user's environment; Goal/Loop/Compact & Resume and multi-worker features build around that bridge. It uses a ChatGPT account's conversations rather than calling Codex directly or assuming the OpenAI API is bundled with a ChatGPT subscription. The project explicitly states that browser integration **is not a public ChatGPT automation API**, may break as the website changes, and may be restricted by provider terms. Use architectural lessons rather than copy its implementation or make compliance claims.

## Existing Equinox foundation (verify/extend rather than duplicate)

- Equinox Browser already binds exact browser instance, context, tab and ChatGPT conversation identity for Auto Continue and Task Capsules. Its bridge exposes bounded ChatGPT turn inspection and explicit message delivery for the existing Telegram Chat Bridge.
- In `src/telegram-chat-bridge-controller.ts`, `inspectBinding`, `deliverText`, `readFinal` and `startTaskChat` already enforce browser-instance identity, composer readiness, exact task/conversation match, and ambiguous-delivery **no automatic replay**. These are a basis for a **shared native Chat transport adapter**, not a reason to create a second independent DOM automation engine.
- The native UI should use the existing read-only/control-request IPC admission and a small set of narrowly defined chat operations. Only the local backend reaches the Equinox Browser bridge; HTML never receives arbitrary Chrome automation, filesystem or raw Local tool access.
- The browser remains the underlying ChatGPT session authority, with explicit user-owned sign-in in Chrome. Do not copy Chrome login cookies into Electron or pretend a provider account is an official API credential. ChatGPT plan/limits do not equal API entitlement.

## Minimal, usable vertical slice

1. Observe an existing ChatGPT conversation by exact browser context, instance, tab and conversation ID, exposing its title, current turn status and latest authorized visible messages through a bounded existing browser bridge. Handle disconnected, unavailable, refused and stale bindings visibly.
2. Build a **native** Chat section within Control Center: chat list/selection, own composer, conversation feed and streaming/progress/tool indicators with user-friendly states, not a transplanted web page. Reuse the existing visual language rather than adding another application's UI shell.
3. Send text through the shared bounded delivery operation with unique delivery identity, readiness checks, and a clear ambiguous result when the send may have crossed the browser boundary. Never silently retry a potentially committed send. UI reads back exact conversation/turn outcome.
4. Tie a chat to optional Equinox Task Capsule and existing notifications/continuations only on explicit selection. Do not automatically switch between Nyx (Codex), Hemera (Claude Code), Asteria (Antigravity) and ChatGPT just because the companion graphic changes.
5. Later: conversation creation, attachments, per-chat model/effort controls and specialized external agent adapters **only after** confirmed support and manual validation. Unsupported controls must not be decorative or fake.

## Bounded history slice (2026-11-21)

The native Chat pane can import up to **12 most recently rendered turns / 24 text messages**, scoped to an explicitly selected exact ChatGPT browser instance and conversation. Equinox Browser **1.2.4** advertises `chatBridge:10` and adds the read-only `chat_bridge.recent` operation. It returns only text, role, bounded ID and truncation flags from the current DOM, never cookies, HTML, unbounded page data, hidden tokens or tool invocation privileges. The payload is capped at 3,500 Unicode characters per message and 46,000 total code points; legacy role nodes have a limited fallback. Before and after reading, the extension rechecks the selected conversation ID. The shared Local bridge checks instance identity, exact tab and v10 capability before importing. If Chrome is older, this import fails gracefully and local user-initiated sends can still use v9.

The user browser may virtualize old turns, so this is *recent rendered history*, not a complete cloud archive. The native UI labels missing historical data and retains its independently confirmed local sending receipts. No chatgpt.com embedding. Future intermediate updates/tool cards require separately proven DOM semantics rather than inventing cards.

## Coarse live generation state

The existing, read-only Chat Bridge inspection exposes `generationActive` from Equinox Browser's own continuation observer. The native Chat turn state uses this as a **coarse in-progress indicator**, including when generation begins outside the native composer. It does not pretend to stream partial assistant text or tools: `chat_bridge.inspect` remains text-free, `chat_bridge.read_final` exposes only the exact completed assistant turn, and the new bounded `chat_bridge.recent` v10 reads only rendered historical user/assistant text. True intermediate tool cards still require separately validated, scoped semantics, not another scraping engine or fabricated activity. An in-progress assistant output is omitted from the v10 history projection until complete.

## Task Capsule identity in Native Chat

When the selected conversation belongs to a known Task Capsule, the first-party Chat header displays its title and status **only if both the conversation ID and the exact current-user Browser instance ID match** the Task Capsule chat binding. Existing unbound ChatGPT conversations show no invented task association. This is read-only presentation from the existing bounded Tasks API; it does not impersonate agent execution, create a task or expose new task mutations.

## New conversation action (2026-11-21)

The Native Chat sidebar now exposes **New Chat** and Cancel. This is an explicit first-message workflow: the user writes a single line (1–1,500 characters), then clicks Send. The backend creates a durable, generic Task Capsule without copying the user's prompt into it, invokes the existing guarded `telegramChatBridgeController.startTaskChat` with the original user text, confirms the exact new Chrome tab/conversation and binds the Task Capsule before updating the selected Native Chat. This does not embed ChatGPT or create an independent automation engine. The source-verified initial-composer inspection requires exactly one visible editor, just like the Browser 1.2.4 send path.

A generated `nch-UUID` request ID is retained in-memory and as a short Task Capsule note. Repeating the same ID with the **same text** in the running runtime returns the original result without another send; reusing it with **different text** is rejected. After restarting, the durable Task Capsule reference prevents silently recreating that request. Ambiguous starts are **never replayed**; user must inspect Chrome and reconcile manually. Only one New Chat can start at a time. A multi-line first turn is intentionally not accepted by the existing bounded `startTaskChat` protocol; subsequent messages in an established conversation use the normal 4,000-character composer. A separate Cancel action clears a New Chat draft without creating a task or tab; switching threads with unsent text is blocked to prevent cross-conversation misdelivery.

The new action has passed the real private Control API dispatcher in an ephemeral in-process run with a fixed, synthetic Browser bridge and durable-style Task Capsule stub, including repeated-ID and restart replay rejection. The **actual packaged Electron Chat HTML/preload and form submit handler** have also been exercised in an isolated Electron QA app: exactly one task, one first-turn dispatch, one persisted binding and one user/assistant bubble, with a deliberately synthetic answer. The full new-message path against live ChatGPT must still be verified after the matching Source Factory backend is installed. The visual companion picker is not an adapter for separate Nyx/Hemera/Asteria model runtimes. Tool/result cards and interim assistant progress are still separate unfinished Browser observation capabilities.

## Ephemeral live assistant preview (2026-11-21)

Browser source **1.2.5** advertises Chat Bridge v11 and introduces a separately scoped `chat_bridge.live` read-only projection. It confirms the exact authenticated Chrome tab, conversation, current user epoch and active generation state, then reads only the current assistant subtree (at most 3,200 rendered Unicode code points). Before returning any text, it rechecks the tab and turn identity and whether generation is still active. A mismatched or completed turn yields no preview. The native controller uses this capability only when the installed Browser advertises v11, so users on v9/v10 retain existing generation status without spurious capability errors. The UI renders the partial text in a dashed **Live preview** bubble which is explicitly **not** appended to committed messages; completed `read_final` replaces it. No tool calls, result cards, raw DOM, attachments or credentials cross this boundary. Those still require separately grounded provider DOM semantics, and the bridge remains subject to ChatGPT UI changes.

## Risks and real acceptance

- ChatGPT UI/browser extension interaction is **not an official service API**. Document account-policy risks and avoid abusive automation or workarounds to provider restrictions. Prefer supported interfaces where available; no promise that one login can power every agent backend.
- Verify actual user-session ChatGPT text send, observable assistant progress and final output, conversation identity, interruption and uncertain-delivery handling on macOS and Windows. Check native UI layout, role-private data, logs, no localhost dashboard, no extra runtime owner, and signed Main gates. No physical Windows ARM64 device test is required.
- The abandoned `WebContentsView` proof established only that logged-out ChatGPT HTML can render. Its uncommitted native-web-embed implementation was **fully reverted**, its temporary QA app shut down and profile/files removed; it is **not** the desired product and must not be revived.

No automated test suites may be added to the repository. This plan is not a shipped feature.
