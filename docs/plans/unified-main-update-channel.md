# One update stream: signed Stable bootstrap → admitted Main

Status: **IN PROGRESS; not shipped to installed Stable clients**. Product owner decided on 2026-10-11 to remove the long-lived Stable/Main channel choice and avoid repeated numbered Stable releases. The only regular update channel will be admitted, exact-SHA `main-snapshot`; Stable becomes the signed installation and rollback baseline.

## Product contract

- Every new public installer downloads the most recent signed Stable baseline, performs native install, verifies runtime health, then automatically enrolls the installed source in admitted Main using the existing product-owned, pinned toolchain and rollback-capable managed-source enrollment. No channel-choice UI or terminal flag is required.
- Once enrolled, the ordinary Control Center `Check for updates` / `Update & restart` uses only the immutable, four-target-validated `main-snapshot` pointer. Docs-only commits do not create updates. The Chrome Web Store Browser extension has its own channel.
- An existing signed Stable installation (including 6.0.3) **must receive one final signed transition bridge** via its existing old Stable updater; pushing code to public Main cannot modify an installed Stable user's running update engine. The 6.0.3 updater **checks** for updates automatically but does not **apply** them automatically: existing users must complete ONE signed **Update & restart** action before the subsequent Main enrollment happens unattended. Do not promise a forced silent update to already installed 6.0.3 clients. The bridge activates the signed baseline first, health-checks it, enrolls its exact source SHA in managed Main, restarts the owned runtime, and verifies `managed-source` plus exact SHA; no user reinstall, tunnel-key prompt or loss of configuration. The bridge must work on macOS ARM64/x64 and Windows x64/ARM64.
- Source enrollment failure must not remove credentials, native Browser host, user workspace, tunnel profile or stable rollback artifacts. The bridge either automatically restores the healthy signed Stable baseline and reports a redacted retryable error, or retries only with bounded safe policy after recoverable conditions are met; never mark Main enrolled without the durable `install.json`/`current-source.conf` pair and healthy process.
- A healthy existing managed Main install stays Main on repeated installer invocations and restarts. Do not move the Mac mini's factory Developer role onto public Stable.

## Checkpoints

1. **Bootstrap defaults and communication (this PR):** public macOS and Windows installer forward enrollment by default after Stable health, existing internal explicit flag remains accepted for compatibility; docs/Control Center replace the dead-end toggle guidance with automatic Main explanation; contract tests verify forwarding. This alone does **not** upgrade older installed Stable machines.
2. **Existing Stable bridge (implemented; installed-host acceptance pending):** the *new signed helper* activates Stable and checks health before exact-release-SHA Main enrollment, owned restart and Main health confirmation. Failure returns to the signed Stable baseline using verified pointer/stamp rollback. This includes an exact-owned orphan-pointer rollback when an enrollment fails before writing its commit stamp. Injection tests cover success, failure, invalid identity, idempotency and both OS families. Real installed upgrades are a separate gate. **Important platform asymmetry:** Windows WPF launches the new signed release helper during the update, whereas macOS old Stable launches its old helper. The new macOS runtime therefore schedules a detached NEW-release bridge worker after seeing a previous Stable version; that worker waits for the legacy updater to persist signed Stable activation success, then writes a once-per-target-version bounded attempt receipt before migrating. Fresh first installs continue to use installer-owned enrollment; failure does not create a restart loop.
3. **Four-platform acceptance:** added a fast, ephemeral **native filesystem** Stable-to-Main migration and rollback smoke for macOS ARM64/x64 and Windows ARM64/x64 CI lanes; it reads the real OS managed current pointer, validates release.json and owned runtime file layout, exercises the shared exact-SHA bridge and verifies preserved tunnel profile/runtime key after success/failure. The macOS ARM64 fresh-install package acceptance additionally exercises the shared migration bridge with a REAL disposable LaunchAgent and Control Center after an exact validated pointer rollback, forces failed Main health and proves the signed Stable runtime remains launchable, then restores Main; Windows real installer acceptance now verifies that the default installer alone enrolls Main without the legacy opt-in switch. These hosted acceptance tests are not the same as an OLD signed 6.0.3 updater performing a NEW signed bridge upgrade. Next add real native shell signed upgrade/bridge + Main snapshot acceptance and verify WPF ownership/Chrome/WinApp/tunnel state. No installer ZIP or native artifact is trusted without exact source/size/signature/ownership gate.
   **Manual native running-host gate (optional, not on routine PR CI):** dispatch the pre-existing `Main Installed Upgrade Acceptance` and `Main Windows Installed Upgrade Acceptance` workflows with `stable_bridge_acceptance=true` on the exact PR SHA/ref. Each dispatch runs native arm64+x64 disposable hosted runners in parallel. macOS builds the unsigned candidate and exercises a REAL isolated LaunchAgent + Control Center through Stable→Main, forced unhealthy Main→Stable rollback, and recovered Main; Windows builds the native WPF candidate and exercises real Windows installer defaults, shell runtime restarts, exact SHA migration, forced rollback and re-enrollment, preserving native host state. These workflows deliberately skip their historical Main→Main jobs when the flag is true. **Unsigned disposable test builds cannot establish real signed 6.0.3→final bridge provenance and are not permission to publish a release**; keep the separate signed-production upgrade verification before ending this migration.

### Existing 6.0.3 signature compatibility — pre-release checkpoint

- On 2026-10-11, all four **live** Stable update manifests (macOS arm64/x64 and Windows arm64/x64) returned version `6.0.3` and passed the same `validateSignedUpdateManifest` verifier as the installed updater with shipped `EQUINOX_LOCAL_UPDATE_KEYS`. Their key ID is `stable-2026-01`; the published v6.0.3 trusted key has SHA-256(SPKI DER) `3c76e65b52f4b1ed0cd823f4d2ee3083ec7290657eea125bb35e54f3439058b1`. Preserve that **exact public key identity** until all old Stable users are bridged. Key IDs alone do not make a different key compatible. `git diff v6.0.3 -- src/equinox-local-updater.js src/equinox-local-update-keys.js scripts/release/sign-update-manifest.mjs` showed **zero differences** at the checkpoint: the offline protocol preview exercises the exact old verifier and signer contract, not a newly relaxed successor.
- `tests/release/equinox-local-stable-main-signing-compatibility.test.js` runs an offline, four-target `6.0.4` **metadata protocol preview** with an ephemeral test-only Ed25519 key in memory. The existing updater must accept correctly signed manifests with the injected preview trust key and reject version/digest edits; the **real production keyring must reject these test signatures**. The fixture artifacts are small synthetic payloads, not executable releases. This intentionally neither needs nor handles a production private key, nor writes to publishing locations.
- **Remaining production-signed boundary:** the immutable canonical new source commit must have its numbered Stable version bumped, all four exact release archives packaged/CI admitted, and the production signer invoked only via its existing private FD 3 signing interface outside the repository. The real final manifests must pass the **already shipped 6.0.3 public keyring** and match archive SHA-256/byte counts. Old 6.0.3 updaters then need a native hosted signed upgrade rehearsal (including failure rollback) before publishing the new Stable manifest/URLs. Do not substitute the offline preview or hosted unsigned application smokes for this gate; do not expose signing keys or publish a pre-release signing test through live Stable endpoints.

4. **One final signed migration Stable:** combine PRs #193 and #194 plus this channel migration into the next signed Stable; only publish after CI and factory signing gates. Upgrade the Mac mini Developer factory locally and verify version/Doctor, then verify real Windows 6.0.3→bridge→Main update and sustained MCP/Agent Browser/WinApp. The installation process stays Stable *as a recovery baseline*, not a secondary active update channel.
5. **Close legacy surfaces:** remove or repurpose old Stable-vs-Main user controls and notices after verified migration, then close issues #184/#186 and relevant channel debt. Existing user state is never silently deleted.

Do not claim rollout complete before checkpoint 4 and installed-host verification. No fresh release number is approved by this plan alone.
