## Checkpoints

1. **Bootstrap defaults and communication (this PR):** public macOS/Windows installers install Stable by default. The old internal explicit enrollment flag is retained only for compatibility. The user later selects Update & restart to move to Main; tests verify absence of automatic enrollment. This alone does **not** upgrade older installed Stable machines.
2. **Existing Stable bridge (implemented; installed-host acceptance pending):** the *new signed helper* activates Stable and checks health before exact-release-SHA Main enrollment, owned restart and Main health confirmation. Failure returns to the signed Stable baseline using verified pointer/stamp rollback. This includes an exact-owned orphan-pointer rollback when an enrollment fails before writing its commit stamp. Injection tests cover success, failure, invalid identity, idempotency and both OS families. Real installed upgrades are a separate gate. **Important platform asymmetry:** Windows WPF launches the new signed release helper during the update, whereas macOS old Stable launches its old helper. The new macOS runtime therefore schedules a detached NEW-release bridge worker after seeing a previous Stable version; that worker waits for the legacy updater to persist signed Stable activation success, then writes a once-per-target-version bounded attempt receipt before migrating. Fresh first installs continue to use installer-owned enrollment; failure does not create a restart loop.
3. **Four-platform acceptance:** added a fast, ephemeral **native filesystem** Stable-to-Main migration and rollback smoke for macOS ARM64/x64 and Windows ARM64/x64 CI lanes; it reads the real OS managed current pointer, validates release.json and owned runtime file layout, exercises the shared exact-SHA bridge and verifies preserved tunnel profile/runtime key after success/failure. The macOS ARM64 fresh-install package acceptance additionally exercises the shared migration bridge with a REAL disposable LaunchAgent and Control Center after an exact validated pointer rollback, forces failed Main health and proves the signed Stable runtime remains launchable, then restores Main; Windows real installer acceptance tests the legacy explicit bridge separately; default website/Terminal/PowerShell installation stays Stable until Update & restart. These hosted acceptance tests are not the same as an OLD signed 6.0.3 updater performing a NEW signed bridge upgrade. Next add real native shell signed upgrade/bridge + Main snapshot acceptance and verify WPF ownership/Chrome/WinApp/tunnel state. No installer ZIP or native artifact is trusted without exact source/size/signature/ownership gate.
   **Manual native running-host gate (optional, not on routine PR CI):** dispatch the pre-existing `Main Installed Upgrade Acceptance` and `Main Windows Installed Upgrade Acceptance` workflows with `stable_bridge_acceptance=true` on the exact PR SHA/ref. Each dispatch runs native arm64+x64 disposable hosted runners in parallel. macOS builds the unsigned candidate and exercises a REAL isolated LaunchAgent + Control Center through Stable→Main, forced unhealthy Main→Stable rollback, and recovered Main; Windows builds the native WPF candidate and exercises real Windows installer defaults, shell runtime restarts, exact SHA migration, forced rollback and re-enrollment, preserving native host state. These workflows deliberately skip their historical Main→Main jobs when the flag is true. **Unsigned disposable test builds cannot establish real signed 6.0.3→final bridge provenance and are not permission to publish a release**; keep the separate signed-production upgrade verification before ending this migration.

- On 2026-10-11, all four **live** Stable update manifests (macOS arm64/x64 and Windows arm64/x64) returned version `6.0.3` and passed the same `validateSignedUpdateManifest` verifier as the installed updater with shipped `EQUINOX_LOCAL_UPDATE_KEYS`. Preserve that **exact public key identity** until all old Stable users are bridged. Key IDs alone do not make a different key compatible. `git diff v6.0.3 -- src/equinox-local-updater.js src/equinox-local-update-keys.js scripts/release/sign-update-manifest.mjs` showed **zero differences** at the checkpoint: the offline protocol preview exercises the exact old verifier and signer contract, not a newly relaxed successor.

The existing updater must accept correctly signed manifests with the injected preview trust key and reject version/digest edits; the **real production keyring must reject these test signatures**. The fixture artifacts are small synthetic payloads, not executable releases. This intentionally neither needs nor handles a production private key, nor writes to publishing locations.
