# Equinox Local: clean replacement updates (v6)

**Current objective:** Any supported installed v6 version must update to the next admitted Main build without carrying forward executable/runtime files from the previous version. User-owned settings and credentials must survive unchanged. This supersedes the abandoned Guardian eight-stage A/B design from draft PR #230. No new release or production activation has been approved.

## Required behavior

1. The existing signed v6.0.4 Stable-to-Main bridge remains backward compatible with the updater shipped in earlier signed Stable installations. Old binaries cannot be fixed by changing Main source; follow `unified-main-update-channel.md` for the one-time bridge.
2. Every regular Main update stages a **fresh full source checkout and full native release payload** for the device's platform/architecture, under a new immutable version/SHA directory. Validate downloaded signed release metadata/artifact hashes and trusted pinned runtimes before selecting it. Never patch or reuse the previous executable, Node modules, WPF files or Native Messaging host. Use the existing detached updater worker and Windows WPF exit/relaunch or macOS LaunchAgent handoff: the application cannot replace its own running executable.
3. Preserve user-owned configuration **in place**. On Windows this includes `%LOCALAPPDATA%\\Equinox Local\\state` (except bounded temporary updater transactions), user browser profile and workspace. On macOS this includes settings, runtime/tunnel credentials and browser data in `~/Library/Application Support/Equinox Local` plus any external workspace. Keep user settings, tunnel IDs/keys, consent, browser data and preferences. **Do not delete the entire application support/LOCALAPPDATA root**, or use an uninstall that destroys user data.
4. Keep the previous VERIFIED release temporarily for rollback. After shutting down the old runtime, atomically select the new installed release and start its freshly installed shell/backend. One exact source-SHA/HEALTHY check decides success. On failure restore the previous release and automatically launch it. Never commit new-version success before health is proved.
5. On successful health, discard old **product-owned** code/build/cache artifacts, but never user settings, workspace, browser profile or credentials. Fail closed on foreign paths, reparse points, unexpected source hashes and duplicate update processes. Do not manufacture separate quarantine/retirement layers, multiple HMAC command protocols, staged PID/SHA sidecar chains or offline writer-lock ceremonies.

## Acceptance before publishing

- Windows x64 and ARM64: real **already-installed old version → new version** using Update & restart, fresh full native and source files, WPF closed/reopened, correct Native Messaging and working tunnel/runtime, preserved user settings; inject failed target and prove previous version launches automatically.
- macOS arm64 and x64: same cross-version upgrade and rollback with verified LaunchAgent relaunch and preserved user state. Include the existing signed old-Stable-to-Main bridge as a separate compatibility gate.
- CI must measure complete workflow wall time; avoid expensive Windows matrices for documentation-only changes. Test the user-facing update flow, not dozens of intermediate implementation steps.

## Legacy 5.2.1 compatibility discovered by actual installed-host QA

- Real installed signed 5.2.1 on Windows x64/ARM64 and macOS arm64 starts successfully when its **own pinned Node 26.10.0** toolchain is used. Its original Main updater then rejects the larger GitHub compare body (`GitHub response exceeds the size limit.` at 256 KiB), before any B download. The new source's bounded 4 MiB limit fixes **future** Main, **not the already installed 5.2.1 binary**. Never claim that moving the public `main-snapshot` tag repairs the old installed checker.
- A clean, signed, out-of-band repair/reinstall path for affected **already-installed** Main clients remains required. A plain old `--preserve-user-data` uninstall is **NOT an accepted workaround**: already shipped old uninstall code removes secrets, transport and tunnel profile. In this PR the *future* preserve-mode uninstall retains these user-owned files byte-for-byte on macOS and Windows, alongside config/workspace, while removing only product-owned binaries and managed source transactions. Future signed installer + Windows/macOS real preserved-state acceptance must pass before recommending a one-time repair to users.
- The current PR stays Draft: exact candidate Main A→B update, forced failed B→A rollback and legacy recovery are still unproven. Avoid adding a second Guardian or new automatic updater infrastructure.

## Public installer rule (confirmed by product owner 2026-10-16)
The classic Terminal/PowerShell installer installs **Stable**, including when an earlier Equinox Local is already installed. It does **not** move to Main automatically. **Only a user-initiated Update & restart** enrolls Main. Installer reinvocation is the fallback path for an older broken Main updater, preserving user settings and credentials, then exposing the ordinary explicit update action. The Windows native handoff and real old-Main source state require hosted end-to-end verification before claiming this fallback is shipped.


## Classic Stable installer over an already-installed Main

A signed Stable installer may replace a **different** numbered installed Main release by using the existing full native A/B activation and health rollback. During the new Stable launch, the authenticated old Main install stamp is atomically parked; if new Stable fails, the stamp is restored **before** relaunching old Main. The user's config, tunnel credentials, profile and browser data are not touched. A newer signed Main may be replaced by an older numbered Stable on explicit classic installer invocation; a newer installed **Stable** is still protected against implicit downgrade.

**Implementation checkpoint:** same-version Main→Stable full-tree replacement, interrupted-install recovery and health-failure rollback have now passed real installed native acceptance on Windows x64/ARM64 and macOS arm64/x64. This is the *unpublished PR code and disposable CI candidate*, not the old 6.0.4 signed installer deployed to users. Historical already-installed 5.2.1→new production-signed Stable and subsequent explicit Main enrollment are still blocked on separate four-native evidence. Do not advise the old released preserve-mode uninstall—it may delete user tunnel secrets.

### Same-numbered Main repair checkpoint (2026-10-16)

The candidate classic installer now stages a complete signed Stable tree even when its version equals the installed Main version. Its separate, bounded rollback identity is recovered *before* resolving the version-based current pointer, and health must report `managed` rather than merely the same version as the old `managed-source` runtime. Local temporary-filesystem tests cover success, failed Stable health, credentials preservation, interrupted filesystem moves, and resumable cleanup. **Native hosted Windows x64/ARM64 and macOS arm64/x64 installed-5.2.1 acceptance is still required before merge or publication.** The currently published signed 6.0.4 archives embed their original installer helper, so changing Main alone does not update the public Terminal/PowerShell repair flow; it requires a separately signed, newly distributed installer payload, not rewriting existing signed v6.0.4 bytes. Windows acceptance exposed a legitimate first-enrollment state with **no** `state/main-update/current-native.json` yet: the old native WPF and Native Messaging host still belong to the numbered Stable release. The repair accepts this legacy case only after verifying the installed shell bytes against the exact old numbered release and HKCU Native Messaging manifest ownership of that numbered launcher. When recovering a failed candidate, the old numbered release is restored *before* re-synchronizing Windows shell/host, so the registered launcher never remains bound to a temporary backup. Native-store-equipped Main installations retain their original exact-SHA verification path. Current routine CI runs real x64/ARM64 WPF reinstall acceptance with these additional checks; the final signed old-release hosted gate remains outstanding.
